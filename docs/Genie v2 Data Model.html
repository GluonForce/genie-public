Genie v2 Data Model

Three tables. users says who someone is, prototypes says where each prototype stands right now, and events records everything that has happened. Clerk, not the database, decides who is an admin.

Where each piece of data lives

Clerk

Identity and permissions

  • Sign-up, sign-in, email verification
  • publicMetadata.role = "admin" for the two employees
  • Role travels in the session token, and the app checks it on every admin route
Supabase Postgres

Three tables

  • users and prototypes hold the current state
  • events holds the full history
  • A copy of each user's role, for display only
Files

Storage and hosting

  • Supabase Storage: audio chunks, source tarball, static-site tarball, build logs
  • Cloudflare R2: the live static site each prototype link serves
  • The database stores only paths to these files

The tables

userswho One row per person. A Clerk webhook creates it. When someone deletes their Clerk account the row stays, with deleted_at set, so signing up again with the same email does not grant another free prototype.

Role and dates

The app reads role here only to show badges and filter lists. Permission checks use the Clerk session.

prototypeswhere it stands now One row is one prototype, from the first recording to expiry. It always shows the current state. The user dashboard, the admin queue and the build worker all read from it. Rows with status approved are the build queue.

eventseverything that happened One row per action by a user, an admin or the system. Requirement versions and remarks, IP sightings, each build attempt with its cost, every decision and release live here. Filter by prototype_id for a prototype's timeline, by user_id for an account's history, or by ip for the IP flag.

1 · Clerk middleware

/admin and /api/admin need role admin in the session token. Everyone else gets a 404.

2 · API routes

Ownership and current status are checked in the same database update, and the event is written in the same transaction.

3 · Database

Unique and check constraints are the last line: one prototype per email, at most 2 remarks. Browsers have no direct database access.
